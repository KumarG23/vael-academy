## Minimal runtime

The daily launch window is **07:00 inclusive–17:00 exclusive America/New_York, every day** (including weekends and DST transitions). Outside it, deterministic lead scans/polls and the dashboard/CI can continue, but fresh lead inference and worker starts/resumes/handoffs defer until the next opening. Runs already launched finish normally; there is no 17:00 kill, duration/turn cap, quota reset, or permission to use a paid route. Manual `wake` retains intent but cannot bypass the window. `status` exposes the shared `work_schedule` contract (`next_open_at`, `policy: finish_in_flight`). The lead/worker recheck at native launch after preflight so a just-before-close dispatch cannot begin model work after close; no off-hours deferral is a failed task or quota block.

`python3 tools/team.py start ISSUE PROFILE` starts a native developer in tmux (`sol`, `sol-dev`, `astra`, `opus`, `fable`, `argon`, `luna`, `deepseek`, `minimax`, `nemotron`, `cohere`); disabled or active-cooldown profiles fail with an explicit reason. Repeating the command after a session finishes resumes that issue's existing checkout and native conversation for the same owner. `python3 tools/team.py handoff ISSUE PROFILE` performs a lead-authorized quota handoff after confirming the previous worker process has exited, preserving the branch, worktree, WIP/untracked files and handoff lineage (starting a fresh native session on cross-provider transfer and retaining the native session ID on same-provider continuation). `python3 tools/team.py quota [ISSUE] [--decision wait|reassign|escalate] [--to PROFILE]` inspects structured provider cooldown state or records a lead quota decision. `python3 tools/team.py event KIND KEY` records a deduplicated pending-work event without invoking any model, and `python3 tools/team.py plan-exhausted [REASON]` suppresses empty-queue periodic refresh wakeups while the human-gated state is unchanged. `status` shows live sessions, lead profile, disabled profiles and provider quota state. `pause` stops new assignments without killing workers; `resume` reopens assignment. `lead` runs one lead pass and returns without waiting for workers; `wake` records a manual nudge for the next eligible pass. An empty idle queue wakes the lead to inspect the plan and replenish useful work. Existing workers can finish without redundant empty-queue planning.

`tools/usage_analytics.py` records allowlist-validated usage telemetry (`runs`, `quota_events`, `polls`, `github_items`, `rate_cards`) in SQLite and provides idempotent historical import (`python3 tools/usage_analytics.py import --db PATH --state PATH ...`) with zero model calls, and `python3 tools/usage_analytics.py import-wrappers --db PATH MANIFEST` imports explicitly listed operator wrapper/probe logs (keyed by full path, start/exit only from receipts, optional predecessor lineage). Paid-credit model entitlement denials are classified `entitlement_denied`, not quota, so they never become a cooldown to retry. Coverage is limited to imported sources; it is not whole-account usage. Raw error text, prompts, account IDs, credentials and private host paths are never stored in analytics tables or exported.

Lead wake-up receipt: each pass compares current main SHA; actionable issue bodies/labels; tracked blocked-issue bodies/labels; exact actionable PR heads, checks and mergeability; worker starts/exits; quota and pending events; and unconsumed discussion deltas. Unchanged state skips inference regardless of age. The existing timer cadence and exclusive lead lock are unchanged. Every hour the deterministic GitHub scan expands to full discussion history (including deletions); elapsed time alone never launches the model. First/bootstrap passes, corrupt/missing receipt recovery, material changes and an explicit `python3 tools/team.py wake` remain valid reasons. A nudge records durable manual intent rather than deleting a receipt. Planning remains lead-owned when material plan/capacity/dependency state changes; an exhausted-plan marker cannot hide a new human answer.

Discussion observation reads paginated issue/PR comments, inline PR comments and submitted/dismissed reviews for current open issues/PRs, including blocked dependencies. Edits are content-hashed, not based on blanket `updatedAt` noise. Every automated lead/developer comment or review must begin with `<!-- dev-studio:auto -->`; unmarked human replies on the SAME GitHub account remain material. A human quoting the marker later in a comment is not silenced. A first scan baselines prior history and the bootstrap/recovery lead reads existing blocked questions/replies. Successful consumption acknowledges only the observed revision and captured event keys; a reply or nudge arriving during inference remains pending. Failed scans never replace good discussion state or pause unrelated healthy workers; they retry at the next tick with `observation_unavailable`. Reaching the 1,000-item CLI issue/PR result cap is explicitly incomplete, not silently complete.

Attribution records the actual launch path separately from material wake reasons: `systemd` means a user-service invocation (not proof that a timer rather than `systemctl start` initiated it), `manual_start` covers an explicit nudge/direct CLI, and `recovery` identifies missing/corrupt receipt recovery. Historical unrecorded triggers remain unknown. Private per-run `lead-audit-*.json` records pre-pass component hashes, acknowledged receipt state and conservative successful native action-command counts. It does not claim independently verified delivery/usefulness or a post-pass GitHub rescan. SQLite completion normalizes wake-reason lists before binding; terminal logs reconcile freshly completed lead rows immediately, while live tmux workers remain running. Webhooks and new external endpoints remain deferred; no timer/service/network configuration is changed by this code.

GitHub issue label `team:ready` means assignable under the existing approved plan; the lead may create and apply it itself after checking dependencies and existing issues/PRs. Ordinary plan-grounded tasks do not require fresh human approval. `team:blocked` means a real dependency, model quota, or decision needs attention; remove ready while blocked. The lead must not repeatedly retry blocked work. Native JSON terminal status is checked as well as process exit; recoverable intermediate tool errors do not reject a successfully repaired turn. Resumed directories must still be the correct repository/worktree and issue branch. Accepted milestones become normal plan/status updates, not a second task database. Claude inference settings are ignored for the subscription-only launch, its route is pinned and checked before inference, and inherited cloud/API selectors are removed; CLAUDE.md and native tools remain available. Native session IDs are saved per issue; a checkout without a confirmed session starts a fresh conversation on the preserved branch. Local runtime files contain only launch/session/log data and are private, not product truth.

Runtime assumes an existing non-root development account owns the checkouts, installed native CLIs and supported subscription logins. It has no sudo, no shared-workspace ACL handoff, no credential broker and no in-repo credentials. Ordinary local tools do not require per-turn approval. Existing credential protection, spend limits, destructive-operation boundaries and GitHub authorization still apply. Do not print auth state containing secrets or upload private host paths/model logs. GitHub-hosted CI has read-only repository permissions and no access to the development VM or provider credentials.

A user-level timer may run the lead at intervals; a lock prevents overlapping lead passes. Workers persist in tmux across SSH disconnects; after a VM restart their branches/native sessions remain and the lead resumes them. Do not claim an interrupted model process survived a reboot. Deployment and infrastructure changes are separate from feature development.

New workers require a reachable user systemd manager. Each `start` runs the detached tmux client through `systemd-run --user --scope`; a newly created server belongs to that transient worker scope rather than the lead service. The client returns after dispatch, while the scope remains until its last process exits. New workers share a private `tmux.sock` in the team state directory, with tmux configuration disabled so normal last-session cleanup applies. Subsequent launches reuse that server. This retains the lead's default `KillMode=control-group`; no `RemainAfterExit`, restart loop, or cleanup exemption is used. Native terminal results, exit receipts and GitHub block/pause reporting remain authoritative: a scope being active or inactive is not evidence of model success. A failed scope launch follows the existing blocked-issue/reporting path; there is no unsafe direct-tmux fallback.

`status`, duplicate detection and the three-worker limit count both the private socket and preserved sessions on the old default socket. Existing workers are neither moved nor stopped. To attach to a new worker, use `tmux -S "${VAEL_TEAM_STATE:-$HOME/.local/state/vael-team}/tmux.sock" attach -t vael-issue-ISSUE`. Legacy sessions still use the default socket. Preserve the existing one-controller GUI rule. See [worker lifecycle verification and rollout](WORKER_LIFECYCLE.md) for isolated evidence, limitations and operator steps.
