## Minimal runtime

`python3 tools/team.py start ISSUE PROFILE` starts a native developer in tmux (`sol`, `astra`, `opus`, `fable`, `argon`, `deepseek`, `minimax`, `nemotron`, `cohere`); disabled profiles fail with an explicit reason. Repeating the command after a session finishes resumes that issue's existing checkout and native conversation. `status` shows live sessions. `pause` stops new assignments without killing workers; `resume` reopens assignment. `lead` runs one lead pass and returns without waiting for workers; `wake` forces the next pass to run inference. An empty idle queue wakes the lead to inspect the plan and replenish useful work. Existing workers can finish without redundant empty-queue planning.

Lead wake-up receipt: before inference, each pass digests what it acts on — current main SHA; ready issues' number/title/body/labels; non-draft, unblocked PRs' number/title/labels, exact head SHA, mergeability and check name/status/conclusion; and live worker sessions plus worker exit receipts. If every part matches the last *successful* pass and that pass was under an hour ago, the timer tick returns without model inference. The first pass, any change (new main commit, ready issue content/labels, PR head, CI transition, mergeability, worker start/completion/slot change) or the hourly safety refresh runs a full lead pass, and the prompt states which part changed. Only a successful native turn records the receipt (`lead-receipt.json` in team state: per-part hashes and a time, not a task database); failed preflight/turns pause as before and never suppress the retry. GitHub/git read failures keep the existing pause path. The digest is of the state the lead *saw*, so its own merges/launches wake one follow-up pass rather than being absorbed; run URLs, timestamps and comments are excluded so a pass cannot keep waking itself. The empty-queue case is the same receipt, so unchanged exhausted plans are still reconsidered hourly and a new main commit wakes planning sooner.

Limitation: comment-only changes (a new issue/PR comment or review without a body, label, head or check change) are not in the digest and become visible at the next hourly safety refresh, not immediately. To surface one sooner, change the issue's label/body, or run `python3 tools/team.py wake`, which clears the receipt so the next pass runs inference.

GitHub issue label `team:ready` means assignable under the existing approved plan; the lead may create and apply it itself after checking dependencies and existing issues/PRs. Ordinary plan-grounded tasks do not require fresh human approval. `team:blocked` means a real dependency, model quota, or decision needs attention; remove ready while blocked. The lead must not repeatedly retry blocked work. Native JSON terminal status is checked as well as process exit; recoverable intermediate tool errors do not reject a successfully repaired turn. Resumed directories must still be the correct repository/worktree and issue branch. Accepted milestones become normal plan/status updates, not a second task database. Claude inference settings are ignored for the subscription-only launch, its route is pinned and checked before inference, and inherited cloud/API selectors are removed; CLAUDE.md and native tools remain available. Native session IDs are saved per issue; a checkout without a confirmed session starts a fresh conversation on the preserved branch. Local runtime files contain only launch/session/log data and are private, not product truth.

Runtime assumes an existing non-root development account owns the checkouts, installed native CLIs and supported subscription logins. It has no sudo, no shared-workspace ACL handoff, no credential broker and no in-repo credentials. Ordinary local tools do not require per-turn approval. Existing credential protection, spend limits, destructive-operation boundaries and GitHub authorization still apply. Do not print auth state containing secrets or upload private host paths/model logs. GitHub-hosted CI has read-only repository permissions and no access to the development VM or provider credentials.

A user-level timer may run the lead at intervals; a lock prevents overlapping lead passes. Workers persist in tmux across SSH disconnects; after a VM restart their branches/native sessions remain and the lead resumes them. Do not claim an interrupted model process survived a reboot. Deployment and infrastructure changes are separate from feature development.

New workers require a reachable user systemd manager. Each `start` runs the detached tmux client through `systemd-run --user --scope`; a newly created server belongs to that transient worker scope rather than the lead service. The client returns after dispatch, while the scope remains until its last process exits. New workers share a private `tmux.sock` in the team state directory, with tmux configuration disabled so normal last-session cleanup applies. Subsequent launches reuse that server. This retains the lead's default `KillMode=control-group`; no `RemainAfterExit`, restart loop, or cleanup exemption is used. Native terminal results, exit receipts and GitHub block/pause reporting remain authoritative: a scope being active or inactive is not evidence of model success. A failed scope launch follows the existing blocked-issue/reporting path; there is no unsafe direct-tmux fallback.

`status`, duplicate detection and the three-worker limit count both the private socket and preserved sessions on the old default socket. Existing workers are neither moved nor stopped. To attach to a new worker, use `tmux -S "${VAEL_TEAM_STATE:-$HOME/.local/state/vael-team}/tmux.sock" attach -t vael-issue-ISSUE`. Legacy sessions still use the default socket. Preserve the existing one-controller GUI rule. See [worker lifecycle verification and rollout](WORKER_LIFECYCLE.md) for isolated evidence, limitations and operator steps.
